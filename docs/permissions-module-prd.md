# CLASSCORE — როლებისა და უფლებების მოდული

Transcribed from the uploaded PDF (`classcore_permissions_module_prd.pdf`,
Module Level PRD, v1.0, 13 Sept 2026, დამტკიცებული) so it lives alongside
the codebase and its companion doc, `docs/authorization-module.md`.

## 1. მიმოხილვა და მიზანი

როლებისა და უფლებების მოდული განსაზღვრავს, თუ რისი გაკეთება შეუძლია
თითოეულ მომხმარებელს ClassCore-ში — რა ინფორმაციას ხედავს, რა
მოქმედების გაკეთება შეუძლია, და რომელ მონაცემებზე ვრცელდება ეს უფლება.
ეს არის საძირკვლის დონის მოდული — ყველა დანარჩენი, უკვე დაწერილი და
მომავალში დასაწერი მოდული მასზეა დამოკიდებული.

მოდულის მთავარი პრინციპია მოქნილობა ხისტი კატეგორიების გარეშე —
უფლებები არ არის მუდმივად „მიკერებული" კონკრეტულ როლზე, არამედ
თითოეული ცალკეული უფლების ინდივიდუალურად ჩართვა/გამორთვა
შესაძლებელია კონკრეტულ ადამიანზე, საწყისი როლის მიუხედავად.

## 2. საბაზისო ცნებები

```
Permission (ატომური ერთეული)
  ↓ იკრიბება სახელდებულ კრებულად
Role (Super Admin / Main Administrator / Administrator / Teacher / Student)
  ↓ ენიჭება
User (შეიძლება ატარებდეს 1+ როლს)
  ↓ + ემატება
Override (ხელით დამატებული/გამორთული უფლება კონკრეტულ ადამიანზე)
  ↓ + შემოიფარგლება
Scope (რომელ მონაცემებზე ვრცელდება — კიბის რომელ საფეხურამდე)
  ↓ + შეიძლება დაიბლოკოს
Permission Lock (ზემოთა იერარქიული დონის მიერ, კასკადურად ქვემოთ)
```

| ცნება | განმარტება |
|---|---|
| Permission | ერთი, ყველაზე პატარა, ატომური მოქმედება სისტემაში (მაგ. „ტარიფის წაშლა", „SMS შაბლონის რედაქტირება"). ეკუთვნის კონკრეტულ მოდულს. |
| Role | Permission-ების სახელდებული კრებული — არა „ჭურჭელი" წესებისთვის, არამედ მხოლოდ საწყისი შაბლონი. |
| Override | კონკრეტულ ადამიანზე ხელით დამატებული ან გამორთული უფლება, რომელიც უპირატესია Role-ის დეფოლტზე. |
| Scope | რომელ მონაცემებზე ვრცელდება ეს უფლება — არა მხოლოდ „შეუძლია თუ არა", არამედ „ვისზე/რაზე". |
| Lock | იერარქიულად ზემოთა დონის მიერ დაწესებული, ქვემოთა დონისთვის შეუცვლელი შეზღუდვა. |

## 3. როლების იერარქია

- **Super Admin** — პლატფორმის დონე (ClassCore-ის გუნდი). მოქმედებს ყველა
  სტუდიის ზემოთ, არა ცალკეული სტუდიის შიგნით.
- **Main Administrator** — ერთი, უნიკალური სტატუსი თითო სტუდიაზე. ეკუთვნის
  მას, ვინც პირველად დაარეგისტრირა სტუდია. სრული უფლებები, გამონაკლისის
  გარეშე, საკუთარ სტუდიაში. დეტალურად აღწერილია ავტორიზაციის მოდულის
  PRD-ში, სექცია 7.
- **Administrator** — Main Administrator-ის მიერ დამატებული დამხმარე
  ადმინისტრაციული პერსონალი („ოფის მენეჯერის" ტიპის). შეუძლია
  მოსწავლეებისა და მასწავლებლების მართვა და მათი უფლებების ცვლილება,
  მაგრამ არა Main Administrator-ის შეზღუდვა.
- **Teacher** — მასწავლებელი, სტანდარტულად შემოსაზღვრული საკუთარი
  ჯგუფებით (Scope, იხ. სექცია 4).
- **Student** — მოსწავლე, სტანდარტულად შემოსაზღვრული მხოლოდ საკუთარი
  მონაცემებით.

ერთ ადამიანს შეუძლია ატარებდეს რამდენიმე როლს ერთდროულად (მაგ. იყოს
მასწავლებელიც და მოსწავლეც) — თუმცა ეფექტურად, ერთ მომენტში, მხოლოდ
ერთი როლის „ტანსაცმელშია" (იხ. სექცია 5).

## 4. Scope-ის კიბე

თითოეული Permission ვრცელდება არა აბსტრაქტულად, არამედ კონკრეტულ
მონაცემთა ფარგლებში. Scope აწყობილია იერარქიულ კიბედ — ყოველი ზედა
საფეხური ავტომატურად მოიცავს ყველა ქვედას:

```
platform (ყველა სტუდია)                        ← Super Admin
  studio (ერთი სტუდია, ყველა ფილიალი/ჯგუფი)    ← Main Administrator, Administrator
    branch (ერთი კონკრეტული ფილიალი)
      group (ერთი ან რამდენიმე ჯგუფი)          ← Teacher-ის დეფოლტი
        self (მხოლოდ საკუთარი მონაცემები)      ← Student-ის დეფოლტი
```

მაგალითად, თუ ადმინისტრატორს აქვს `studio` დონის Scope, მას ავტომატურად
აქვს წვდომა ყველა `branch`-სა და `group`-ზე ამ სტუდიის შიგნით, დამატებითი
ცალკეული მინიჭების გარეშე.

## 5. Active Role Only — ეფექტური უფლებების გამოთვლა

თუ მომხმარებელს ერთზე მეტი როლი აქვს, მისი ეფექტური უფლებები ნებისმიერ
მომენტში შემოიფარგლება მხოლოდ იმ როლით, რომელზეც ამჟამად არის
გადართული — არა ყველა მისი როლის ჯამით. ეს პირდაპირ შეესაბამება
ავტორიზაციის მოდულში აღწერილ „როლს შორის გადართვის" მექანიზმს (სექცია
6).

მნიშვნელოვანი დაზუსტება: ეს არის შეგნებული არჩევანი, რომელიც ანაცვლებს
უფრო ზოგად, „ყველა როლის ჯამური უფლების" მოდელს. მიზეზი პრაქტიკულია —
მასწავლებლის რეჟიმში მყოფი ადამიანი უნდა ასრულებდეს მხოლოდ
მასწავლებლის საქმეებს, არა შერეულად მოსწავლისაც. უფლების შემოწმება
ყოველ მოთხოვნაზე ითვალისწინებს არა მხოლოდ მომხმარებლის ვინაობას,
არამედ იმასაც, რომელ როლზეა ის ამ მომენტში გადართული.

## 6. Override მექანიზმი

Role-ის დეფოლტური უფლებები არის მხოლოდ საწყისი წერტილი — ზემდგომ
დონეს (Main Administrator-ს, ან Administrator-ს საკუთარი ფარგლების
შიგნით) შეუძლია ცალკეული უფლების ხელით ჩართვა ან გამორთვა კონკრეტულ
ადამიანზე, საწყისი როლის მიუხედავად.

პრაქტიკაში, ეს ხდება მასწავლებლის მოწვევის ნაკადის ბოლოს (ავტორიზაციის
PRD, სექცია 8) — დასადასტურებელ ეკრანზე გამოსახულია Role-ის დეფოლტური
უფლებები, უკვე მონიშნული, ხოლო ადმინისტრატორს შეუძლია სურვილისამებრ
რომელიმეს ჩართვა ან გამორთვა, დამატებითი ეტაპის გარეშე.

## 7. Permission Lock-ის კასკადი

თითოეულ იერარქიულ დონეს შეუძლია დააწესოს შეუცვლელი შეზღუდვა
უშუალოდ თავისზე დაბლა მდგომ დონეზე — ეს შეზღუდვა ("Lock") ქვედა დონეს
ართმევს შესაძლებლობას, თვითონ შეცვალოს ან გადაფაროს ეს კონკრეტული
უფლება, თუნდაც Override-ის მეშვეობით.

- **მიმართულება** — Lock მოქმედებს მხოლოდ იერარქიულად უშუალოდ ქვემოთ.
  Super Admin ბლოკავს Main Administrator-ს; Main Administrator ბლოკავს
  Administrator-ს, Teacher-სა და Student-ს საკუთარი სტუდიის ფარგლებში.
  თანასწორ დონეზე (მაგ. ერთი Administrator მეორეზე) ან ზემოთ ბლოკვა
  არასდროს დაიშვება.
- **უპირატესობა კონფლიქტის დროს** — თუ ერთსა და იმავე Permission-ზე
  ერთდროულად არსებობს Lock და Override, Lock ყოველთვის იმარჯვებს,
  დაყენების თანმიმდევრობის მიუხედავად.
- **„დაბლოკვის უფლების" საკუთარი Permission** — თავად შესაძლებლობა,
  დაბლოკო სხვისი უფლება, ჩვეულებრივი Permission-ია (არა ცალკე,
  ჰარდქოდირებული წესი) — შესაბამისად, Main Administrator-ს შეუძლია ამ
  კონკრეტული უფლების მინიჭება ან ჩამორთმევაც კი დამატებულ
  Administrator-ზე, იმავე Override მექანიზმით.

## 8. Zone — Dashboard vs მოსწავლის გვერდი

თითოეული Permission ეკუთვნის ერთ-ერთ ინტერფეისულ ზონას — Dashboard
(ადმინისტრატორისა და მასწავლებლის სამუშაო სივრცე) ან მოსწავლის გვერდი.
ეს არის hard constraint, არა override-ადი წესი: Dashboard ზონის Permission
ვერასდროს გააქტიურდება მომხმარებელზე, რომლის ერთადერთი როლი არის
Student — თუნდაც ვინმემ სცადოს მისი ხელით ჩართვა Override-ით.

მოსწავლის საკუთარი გვერდი/ინტერფეისი ჯერ არ არის აშენებული ფრონტში.
ამ ეტაპზე Zone-ის ცნება მხოლოდ მონაცემის დონეზე ფიქსირდება (თითოეულ
Permission-ს გააჩნია ეს ატრიბუტი) — ფაქტობრივი UI-ის დონეზე enforcement
აშენდება მაშინ, როცა მოსწავლის გვერდი დაპროექტდება.

## 9. Permission Registry — მომავალი მოდულების ინტეგრაციის სტანდარტი

რომ ყოველი ახალი მოდულის დამატებისას არ დაგვჭირდეს ამ სისტემის
ხელახალი გადაკეთება, მკვიდრდება მუდმივი წესი: ყოველ მომავალ Module
PRD-ს თან უნდა ახლდეს ამ მოდულის Permission-ების ჩამონათვალი —
თითოეული მოქმედება, რომელიც ამ მოდულში შესაძლებელია, ცალკე Permission
ID-ის სახით (მაგ. `subscriptions.create`, `tariffs.delete`).

ეს ჩამონათვალი ავტომატურად ემატება საერთო Permission Registry-ს, ახალი
როლის თუ სისტემის ხელახალი დაპროექტების გარეშე — ახალი მოდული
უბრალოდ „რეგისტრირდება" არსებულ არქიტექტურაში.

## 10. დამოკიდებულებები სხვა მოდულებთან

| საკითხი | სად აღიწერება |
|---|---|
| Unified Auth, სესია, პაროლი, როლს შორის გადართვის UX, მთავარი ადმინისტრატორის იერარქია | ავტორიზაციის მოდულის PRD-ში (→ `docs/authorization-module.md`). |
| თითოეული უკვე დაწერილი მოდულის (აბონემენტები, ტარიფები, SMS) კონკრეტული Permission-ების ჩამონათვალი | → `src/lib/permissions/registry.ts` (Permission Registry — Registry-ის სტანდარტის მიხედვით, სექცია 9). |
| მოსწავლის გვერდის/ინტერფეისის სრული აღწერა | ცალკე, მომავალში დასაწერ „მოსწავლის პროფილის" მოდულის PRD-ში. |
